# 문서 쓰기 도구 설계 — 열린 에이전트 + 자기검증 도구

상태: 설계 (draft)
날짜: 2026-07-26

## 철학

이 에이전트는 **열린 에이전트**다 — 자원을 자유롭게 오케스트레이션한다. 문서 편집을 위해
사람이 정한 연산 목록(닫힌 프로토콜) 안에 에이전트를 가두지 **않는다.**

대신 각 형식마다 **좋은 편집 방법을 "자기검증하는 도구"로 감싸** 제공하고, 에이전트가
그 도구를 쓰도록 **유도**한다. 품질과 안전의 책임이 "에이전트를 가두는 프로토콜"이 아니라
**(1) 도구 자신의 자기검증 + (2) 승인 게이트**로 옮겨간다.

    닫힌 프로토콜(v2):  에이전트는 정해진 연산만 뽑을 수 있다        ← 우리가 버리는 것
    열린 에이전트(우리): 에이전트는 자유롭되, 쓰기는 좋은 도구로 유도  ← 우리 방식

### v2에서 프로토콜 없이 가져오는 안전 아이디어

닫힌 프로토콜을 버려도 그 안전망은 버리지 않는다. **각 도구 안에** 심는다:

- **후보 우선(candidate-first)** — 원본을 바로 덮지 않고 후보 파일을 먼저 만든다.
- **자기검증(self-verify)** — 후보를 다시 파싱해 편집이 실제로 됐는지 확인, 안 맞으면 **거부**.
- **현재값 대조(expected)** — 바꾸기 전 현재 내용이 기대와 같은지 확인(엉뚱한 대상 방지).
- **본 것 = 적용** — 승인은 그 후보를 그대로 커밋. writer를 재실행하지 않는다.

## 쓰기 도구 계약 (모든 형식 공통)

모든 문서 쓰기 도구는 이 계약을 지킨다. 도구는 **제안·검증만** 하고, 실제 커밋은
승인 게이트 뒤의 결정적 executor가 한다.

```
tool edit_<format>(target, <edit args>, expected?):
    1. 대상 경로가 등록 워크스페이스 안인지 확인 (밖이면 거부)
    2. 원본 읽기 → base_sha256 계산
    3. 후보 생성 (원본은 그대로) — 형식 전용 라이브러리로 편집
    4. 자기검증: 후보를 재파싱해 편집이 실제로 반영됐는지 확인
       · 안 맞으면 WriterError 로 실패 (부분 결과·깨진 파일 남기지 않음)
    5. 반환: proposal { tool, target, base_sha256, preview, candidate_id }
       · 커밋하지 않는다
    ── 여기서 승인 게이트가 preview 를 사용자에게 보여준다 ──
    6. 승인 시: base_sha256 재확인 → 백업 → atomic replace → journal(undo)
```

`preview` 는 형식에 맞는 before/after(텍스트 diff, 또는 렌더 이미지 쌍)로 낸다.
승인 창이 이걸 보여주지 못하면 "무엇을 승인하는지" 알 수 없으므로, preview 생성은
도구의 의무다.

### 위험 등급 (tool_risk)

- 모든 문서 쓰기 도구 = **CAUTION** → 승인 게이트를 거친다(파일을 바꾸므로).
- 문서를 **raw 로** 다루는 것(`Bash` 로 바이너리 조작, `Write` 로 hwp/docx 직접 쓰기) =
  **DANGER** 로 올린다 — 검증 없는 원본 훼손이 가능하기 때문. 유도(아래)로 애초에 그쪽으로
  가지 않게 한다.

## 형식별 도구

| 도구 | 형식 | 엔진 | 자기검증 |
| --- | --- | --- | --- |
| `edit_hwp_form` | HWP·HWPX 양식·표 | **rhwp** (셀 인덱스, native exportHwp) | 채운 뒤 재파싱해 셀 단위 대조, 불일치 거부. `.hwp` 원본도 씀 |
| `edit_docx` | DOCX | python-docx | 재오픈해 대상 문단/셀 값 확인 |
| `edit_xlsx` | XLSX | openpyxl | 재오픈해 셀 값 확인 |
| `edit_pptx` | PPTX | python-pptx | 재오픈해 대상 텍스트 확인 |
| `edit_pdf` | PDF | PyMuPDF | 주석·폼필드·가림을 파생 사본에 적용, 재파싱 확인 |
| `edit_text` | MD·TXT | 앵커 치환(기존 change-plan) | 앵커 유일성 + 해시 확인 |
| `create_document` | 신규 | 형식별 writer | 생성 후 재파싱해 기대 낱말 비율 확인, no-overwrite |

**HWP 는 rhwp 가 담당한다** — kordoc은 병합셀 표를 마크다운 왕복에서 뭉개므로(측정: 3~17%
잔존) 양식·표에 부적합하다. rhwp는 논리 셀을 인덱스로 직접 읽고 쓰며 `.hwp` 원본까지
내보낸다. 채운 사본을 만들어 셀 단위로 검증하므로 계약의 자기검증도 이미 만족한다.

## 에이전트를 좋은 도구로 유도하는 법 ("좋은 방법만 소개")

프로토콜로 강제하지 않으므로, 유도는 세 겹으로 한다:

1. **도구 큐레이션** — 위 자기검증 도구만 노출한다. raw 바이너리 편집 경로는 도구로
   제공하지 않는다(가능은 하되 DANGER 로 분류돼 눈에 띄게 승인을 받는다).
2. **도구 설명** — 각 도구 설명에 "언제·왜 이 도구인지"를 적는다. 예:
   > `edit_hwp_form`: 한글(HWP/HWPX) 양식·표를 셀 단위로 안전하게 채우고 고친다. 표
   > 구조를 보존하고 원본을 검증하므로, HWP/HWPX 편집은 반드시 이 도구를 쓴다. `Bash`·
   > `Write` 로 hwp 파일을 직접 만지지 말 것.
3. **시스템 프롬프트** — "문서를 고칠 때" 절(아래 instructions.py 반영)에서 형식별 도구를
   우선하고 raw 편집을 피하도록 명시.

에이전트는 여전히 열려 있다 — 프로토콜이 예상 못 한 일(여러 형식 조합, 다단계 작업, 새
스크립트)도 한다. 유도는 **쓰기의 품질 경로**를 가리킬 뿐, 에이전트의 자유를 막지 않는다.

## 한계 (정직하게)

- 품질은 **확률적**이다 — 유도가 실패하면 나쁜 경로를 택할 수 있다. 완화: 자기검증 도구가
  나쁜 결과를 거부 + 강한 유도 + 승인 게이트. "보장"이 아니라 "매우 그럴듯함".
- **도구가 진짜 좋고 자기검증해야** 의미가 있다. "python-docx 를 Bash 로 쓰게 해줌"은
  깨진 파일을 낳는다 — 반드시 검증 래퍼로 감싼다.
- 미리보기를 도구가 만들어야 승인 창이 성립한다.

## 구현 순서 (제안)

1. 쓰기 도구 계약을 코드로 고정 (`ProposedWrite`/`WriterError`, 후보→검증→proposal).
2. `edit_hwp_form` (rhwp) 을 계약에 맞춰 도구로 노출 — 이미 fill.ts 가 자기검증하므로 래핑 위주.
3. `edit_text`(기존 change-plan) 를 계약 형태로 정리.
4. `edit_docx`/`edit_xlsx`/`edit_pptx`/`edit_pdf` 검증 래퍼 추가.
5. `tool_risk` 에 문서 쓰기 도구 = CAUTION, raw 문서 조작 = DANGER 반영.
6. 시스템 프롬프트·도구 설명에 유도 문구.
